# A–G 正文图版与 Demo 一致性审计

## 审计口径

- 本文记录当前代码事实，不记录任务流水。图版数按课程 JSX 中的 `<figure>` 实例计，Demo 数按实际挂载的 `components/demos/` 组件实例计。
- A/B 上一阶段未被审计是范围遗漏，不代表它们已达到正文标准；本次已补入同一口径。
- 当前 37 门课程共有 **111 个正文图版、55 个 Demo**。唯一没有可操作 Demo 的课程是 G/plug「插头 DP」。
- solver、输入合同、`StepPlayer` 和家族游戏逻辑是稳定边界；本轮只统一表达壳层、交互语法与可视状态。

## 总体结论

- 现有图版都在表达真实算法对象，但几何语言分散：同一状态语义会被矩形填色、发光、文字标签或边框分别表达，无法跨课复用认知。
- 共享 `demo-workbench.css` 只是样式汇流，不是组件合同；工具顺序、进度、速度、参数区、状态说明仍由每个 Demo 自行组织。
- 横向滚动由多个课程 CSS 独立声明，缺少粘性表头、边缘提示、位置概览和统一键盘语义。
- 移动端多数是断点堆叠或缩小，尚未形成“算法主脊柱常驻、细节原位切换”的语义重排。
- 深浅主题大体共用 DOM，但局部状态依赖单一颜色或发光；必须补第二编码。
- 完成态、播放态和 reduced-motion 没有全站统一的演绎合同。

## 统一改造优先级

1. 先建立 `DemoWorkbench`、`InstrumentRail`、`DemoTableViewport`、`DemoDetailSwitch` 和 `VizStateRole` 的真实共享合同。
2. 用 A/01、B/lcs、C/stone、D/grid、E/basic、F/knapsack、G/board 覆盖七种家族材质和主要交互形态。
3. 对高风险课优先处理：A/cost2d、B/edit、C/tree、D/matpow、E/inout、F/knapsack、G/tsp 与 G/plug。
4. 全课程完成后，任何图版或 Demo 都不得通过页面横向滚动、桌面画面裁切或卡片堆叠来解决移动端。
